# Billing validation control operations

## Scope and current readiness

Task 6 supplies a control-plane evaluator and injected provider adapters. The checked-in tests use mocks only. This is not permission or a procedure for a live Stripe/Supabase run: the current validation child is `MIGRATIONS_FAILED`, so integration readiness is **BLOCKED**, not passed. Do not call provider APIs, install DDL, read `.env*`, use a local database, or run candidate/application scripts as part of Task 6.

The controller preserves the pinned registries of 45 financial cases and 15 supervised 3DS cases. `initial.challenge.incomplete` is an additional control-only negative case, not part of the supervised 15. Financial execution currently has fixed contracts only for `payment.approved`, `payment.declined`, `payment.3ds`, `payment.refresh`, and `payment.two-tabs`. Other registered financial cases have no executable outcome contract and refuse closed. The 3DS upgrade, add-area, and off-session renewal challenge cases remain unsupported until their operation-specific trusted evidence is implemented. `initial.webhook_delayed` has a separate two-phase contract described below; it does not use the unchanged-database replay contract.

## Trust and mutation boundaries

An observation pass checks the current Task 5 attempt/fence before and after provider/database reads. Mutations go only through the injected adapter, after a current-fence check, with the exact Task 4 verified TEST account and child environment and a controller-owned, attempt-tied idempotency key. The provider/action allowlist is closed: Stripe checkout replay, Checkout Session expiration, and subscription cancellation; Supabase `fixtures.cleanup` only. Task 4's Stripe runtime remains read-only.

Replaying an application checkout request preserves the application's persisted quote-scoped idempotency key and frozen request. The controller's provider mutation uses a separate per-attempt idempotency key; it must not rewrite the application's key or create a different request payload for the same app replay.

Paid success requires injected Stripe, webhook, and exact Supabase observations. When the expanded `payments` object is present, its `data` list must be complete (`has_more === false`) and its distinct PaymentIntent identity must exactly match the expected PaymentIntent; multiple distinct identities or an incomplete/unknown pagination state fail closed. Only when `payments` is absent may the legacy `invoice.payment_intent` field supply that identity. A new settlement must match the expected contract, and only active grants newly present beyond the baseline count; the complete active-grant set must exactly match expected access. Expected outcome comes from the frozen scenario contract, never a caller override. An empty or missing expected-access set is invalid. Challenge success additionally requires Stripe `authenticationResult === 'authenticated'` and a Task 7 opaque verifier capability bound to the current attempt, current fence, case, and PaymentIntent. A null `authenticationFlow` may be observed, but is not proof by itself. Operator acknowledgement, booleans, and arbitrary JSON are never payment or challenge evidence. Reader exceptions map to finite sanitized refusals such as `observation_read_failed`; raw exception text is never returned.

## Task 7 headed operator and disposable runner boundary

The browser/operator transport is Playwright's `BrowserServer`, not a generic WebSocket server: `playwright-core` is pinned to `1.62.1`, matching the Playwright browser image version. The trusted collector starts headed Chromium with `host: '127.0.0.1'`, `port: 0`, and a fresh 256-bit `wsPath`, then connects with `chromium.connect(endpoint)` inside the same disposable runner. The endpoint and path remain process memory only. Never print them, publish them as an output/artifact, configure `BILLING_3DS_OPERATOR_ENDPOINT`, create an SSH tunnel, or use `exposeNetwork`. The path is a bearer capability: anyone who learns it can control the runner's OS user, so the runner must remain isolated and one-job disposable.

The local operator panel exposes only `complete`, `checkpoint`, and `abort`. Each accepted signal has an exact schema, candidate SHA, attempt, case, and one-use nonce; payment, authentication, pass/fail, and delivery fields are rejected. The resulting in-process capability is bound to the exact immutable Task 6 request (attempt, fence, case, and PaymentIntent or event), expires, is single-use, and is invalidated on close. `runCollect()` ignores scenario-hook return values and returns only Task 6's independently observed result. Browser disconnect, preparation failure, and normal completion close the panel, context, BrowserServer client, server, and pending capabilities. This transport never extends or releases the Task 5 lease. Only trusted collector hooks may initialize the Preview browser or prepare an approved scenario; do not check out or execute candidate-provided code.

`runner/Dockerfile` requires a digest for the Playwright `v1.62.1-noble` base and a version plus SHA-256 for the GitHub runner archive. The image is not built by this task. The entrypoint is restricted to `lawxcompany-stack/billing-validation-control`, accepts only a 128-bit per-attempt label, registers with `--ephemeral --disableupdate --no-default-labels`, runs once, suppresses runner configuration output, unsets the registration token, and removes local runner credential files on success, failure, or cancellation. `--disableupdate` requires a reviewed image-update cadence; do not use a stale runner image.

`runner/supervisor.mjs` is the executable Task 7 orchestration contract. It issues Docker CLI operations through the injected `processBoundary`; it creates both per-attempt bridge networks, reads their actual `docker inspect` state, creates/starts/inspects the proxy, starts and probes `Xephyr :99`, creates/inspects/starts/waits for the runner, then discovers and removes only resources bearing its fresh run label after re-inspecting their identities. It fails closed for unexpected peers, non-internal runner topology, unpinned images, additional mounts, host namespaces, malformed inspection output, or cleanup ambiguity. The default `runner/process-boundary.mjs` uses `spawn` with `shell: false`, bounded stdout, finite timeouts, signal cancellation, and sanitized failures; tests replace this low-level boundary with deterministic Docker/process mocks.

The process boundary refuses to run unless Docker context `billing-validation-isolated` is explicitly selected and prefixes each Docker command with `--context billing-validation-isolated`. This name is a configuration requirement, not proof of the endpoint: the implementation does not inspect or attest the context target. Task 0/9 must verify that it points to the dedicated disposable workstation before any invocation; never substitute `default`, `dev-note`, or the shared runner host.

The runner attaches only to the inspected Docker-internal network; the proxy alone attaches to the per-attempt external network and is the only internal peer. The runner has no Docker socket, host networking, home/project mount, candidate checkout, or other host bind. Its only binds are the nested Unix display socket and a one-run Xauthority file, both read-only. The Xauthority cookie and temporary path exist only in memory/temp state; the headed browser receives `DISPLAY=:99` and `XAUTHORITY=/run/billing-validation/Xauthority`. The same pinned image carries a small HTTPS CONNECT proxy which accepts port 443 only, permits the fixed GitHub system hosts plus exact per-attempt destinations, rejects broad wildcard additions, and refuses DNS answers in private, reserved, loopback, link-local, or metadata ranges. The runner's internal network has no direct external gateway, so an application that ignores proxy variables still has no Internet route.

## Webhook resend and replay evidence

Stripe's [Events API](https://docs.stripe.com/api/events) exposes event listing/retrieval; the [webhook endpoint API](https://docs.stripe.com/api/webhook_endpoints) manages endpoints and does not provide an event-resend mutation. In the pinned application flow, resend is a Dashboard/manual checkpoint. Task 6 therefore asks an injected Task 7 checkpoint provider for an opaque capability bound to attempt, fence, case, and event; the checkpoint proves no outcome and causes **no Stripe mutation call**.

For `initial.webhook_replay`, the checkpoint clock starts only after Task 7 verifies that the manual action is complete; requesting a checkpoint or acknowledging it does not establish an outcome. After that point, the controller independently re-reads the event, endpoint configuration, signed-delivery receipt, processed inbox evidence, and exact financial snapshot. Pass requires a fresh matching verified receipt after the checkpoint, processed inbox evidence, and an unchanged financial snapshot. The event creation time, receipt `receivedAt`, and inbox `receivedAt`/`processedAt` must each be no earlier than the case start and no later than the authoritative database snapshot's `observedAt` cutoff. `pending_webhooks = 0` alone is insufficient. The inbox's existing processed state may predate a new append-only receipt; the receipt itself must be fresh. Endpoint ID/URL are verified as configuration for the event's time window. Delivery receipts do not bind endpoint ID, so results do not claim per-delivery endpoint attribution.

`initial.webhook_delayed` is a separate two-phase transition. Before requesting the verified manual checkpoint, the same Stripe TEST `invoice.paid` event must have `pending_webhooks > 0`, and an exact snapshot digest bound to the initial trusted observation must show zero settlement, grant, revision, and usage delta. Its paused prestate may have either no inbox row and zero receipts, or a matching unprocessed inbox in `pending`, `processing`, or `failed` state with matching attributed receipt data; a processed row is never valid. After checkpoint verification, the same event must complete (`pending_webhooks = 0`) with a fresh matching signed receipt after the checkpoint and within the post-state `observedAt` cutoff, plus a matching processed inbox whose `processedAt` is strictly after the checkpoint and whose timestamps are ordered and bounded. The controller then independently re-observes Stripe and Supabase: the post-state snapshot digest must match that re-observation, which must reconcile one settlement for the expected contract and exactly the newly created expected active grants. The event ID is bound from the initial trusted Stripe observation, not fixture input. This branch is not allowed to inherit replay's unchanged-database rule, and checkpoint capability alone never proves the result. Task 6 does not require a UI/browser witness; Task 7 owns that transport/UI boundary.

## Cleanup and retained evidence

Cleanup is ownership-scoped and works in reverse provider-resource order. It expires only open Checkout Sessions and cancels eligible subscriptions. It retains charges, PaymentIntents, invoices, SetupIntents, events, completed/expired Checkout Sessions, subscriptions after cancellation, and customers. Customer deletion is prohibited: Stripe documents it as irreversible and says it immediately cancels active subscriptions and removes stored cards ([Delete a customer](https://docs.stripe.com/api/customers/delete)).

Database resource kinds resolve only through the closed schema-qualified catalog in `src/billing/cleanup.mjs`; caller-supplied table names, unqualified targets, unknown kinds, and `billing_validation_control` are rejected. No auth identity is deleted. The pinned history-delete trigger protects `billing_quotes`, `billing_checkout_attempts`, `billing_contract_revisions`, `billing_change_requests`, `billing_coupon_redemptions`, `billing_usage_events`, `billing_events`, `billing_effects`, `billing_financial_adjustments`, and `billing_audit_log`; `billing_settlement_effects` has its own history-delete trigger and restrictive foreign keys. These records are retained. Task 6 does not disable triggers, bypass foreign keys, or claim to restore the database baseline after a paid fixture.

If the current attempt owns **any** retained database evidence, cleanup refuses success and leaves the Task 5 lease held. An active contract or area grant gets a specific refusal; inactive but immutable evidence also blocks reuse. No release receipt is returned in either case. Where there are no owned database rows and the observed snapshot exactly matches baseline, reversible provider cleanup is followed by a fenced, empty `fixtures.cleanup` callback, fresh re-observation, and only then lease release. In that narrow path `completed: true` means reversible provider fixture actions completed; `fixtureReusable: true` and `databaseBaselineRestored: true` are asserted only after exact baseline verification. Retained provider financial objects are listed explicitly in the result.

The shared validation branch plus Task 5 lease serializes concurrent attempts; it does **not** roll back immutable database history. Paid fixtures can cause cumulative retained-row growth. Before remote provider tests, the project needs an explicit retention limit and branch rotation or an isolated per-attempt fixture/reset architecture. Task 6 does not reset, recreate, or rotate the branch. Live cleanup of retained paid fixtures remains unavailable until that architecture is approved and supplied by the later integration task.

## Output hygiene

Receipts and logs contain only sanitized synthetic/provider IDs, status, timestamps, and digests. Never emit API keys, Stripe client secrets, browser/session state, cookies, private operator capabilities, or raw provider/database rows. Capabilities are verified in-process and are not returned as evidence payloads.
