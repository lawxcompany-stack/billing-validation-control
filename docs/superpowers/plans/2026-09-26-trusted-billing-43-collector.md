# Trusted Billing 43 Collector Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Execute one task at a time with a fresh implementer and independent review. Track all tasks in the plan's SDD ledger.

**Goal:** Replace the incomplete, untrusted financial evidence path with a fail-closed trusted collector that can execute exactly 43 synthetic billing journeys and produce a verifiable, append-only result.

**Architecture:** Keep the control repository as the only source of executable scenario contracts, provider allowlists, retention policy, SQL gates, and result verification. Use a durable ledger for capacity, resource locks, fences, and provider intents; perform browser interaction only through a fixed transport to the immutable Preview, and reconcile all outcomes with independent readers before publishing a sanitized manifest.

**Tech Stack:** Node.js 22 ESM, node:test, PostgreSQL transactions/schema in the private control store, pinned GitHub Actions, GitHub Artifact Attestations, Playwright Core, injected Supabase/Stripe adapters.

**Spec:** docs/superpowers/specs/2026-09-26-trusted-billing-43-collector.md

## Global Constraints

- The exact canonical suite is 43 IDs from the Spec; signup.advbox and payment.3ds are excluded.
- Candidate code is untrusted and is never checked out, imported, or executed by a privileged control job.
- The only later-eligible Supabase target is child validation branch lawx-billing-validation-20260912 (zjvq…); never Supabase main.
- This plan authorizes offline local implementation only: no remote service calls, secrets/configuration changes, migrations, remote tests, push, PR, merge, or deploy.
- Never delete historical rows/Auth users/Stripe customers/payment intents/events/Test Clocks; no branch rotation or auto-purge.
- Missing/invalid retention limits, unhealthy/mismatched environment, ambiguous provider mutation, lost fence, or incomplete evidence fails closed and retains the lock/reservation until independent reconciliation.
- A successful cleanup reports databaseBaselineRestored=false and fixtureReusable=false.
- Stripe idempotency key and Test Clock expiry are provider-managed; never infer or reissue ambiguous operations after retention expiry.
- Keep all PII, cookies, session state, provider payloads, secrets, and raw errors out of logs/artifacts.

## File map and interfaces

- src/billing/fixtures.mjs remains the source for scenario contracts and safe evidence categories; scenario contracts are grouped by domain and exported as an exact registry.
- src/attempts/schema.sql and src/attempts/postgres-store.mjs own durable attempts, append-only reservations/receipts, global resource locks, and provider mutation intents.
- src/attempts/prepare.mjs, lock.mjs, cleanup.mjs, recheck.mjs and store.mjs own admission, lease/fence transitions, reconciliation, and store adapters.
- src/billing/contracts.mjs and src/billing/financial.mjs own allowlisted mutations, durable in-flight intent protocol, common journey execution, and independent evidence assertions.
- src/billing/cleanup.mjs owns owner-scoped reversible provider closure and append-only retention verification.
- src/runtime/* owns fixed HTTP/provider/read-only health adapters; no module accepts arbitrary candidate paths or dynamically imported code.
- src/contracts/evidence.mjs and src/github/ci-evidence.mjs own canonical 43-result validation and candidate artifact rejection.
- src/operator/run-collect.mjs, src/runner/*, and .github/workflows/validate-billing.yml own trusted orchestration and evidence handoff. Activation and result attestations remain separate jobs; provider runner gets no signing permissions.
- policy/candidate-workflows.json and src/github/policy.mjs define the candidate workflow boundary; app PR artifacts are not proof of the 43 journeys.

Cross-task interface: src/contracts/billing-43.mjs exports the frozen ordered BILLING_43_IDS tuple. Domain modules export contract entries shaped {id, domain, maxWrites, allowedOperations, requiredEvidence, async run(context)}; context is an immutable attempt-bound object containing fixture identity, fixed Preview request transport, independent readers, allowlisted mutation adapter, clock, attempt fence and sanitized recorder. A scenario returns only {id, status:'passed', evidence:[closed-schema evidence], resourceIds:[owned synthetic IDs]}. The trusted executor compares the domain contract map to BILLING_43_IDS and refuses missing/extra contracts before any context or mutation; it never accepts status from an app response as the verdict.

Admission interface: prepareAttempt({identity, environment, retentionPolicy, projection}) returns {attemptId, fixtureRunId, fence, reservationId, resourceLocks, capacity}; all identifiers are generated by trusted control code. acquire/renew/assert/release require attemptId and fence. A provider mutation first persists {attemptId, fence, provider, operation, requestDigest, idempotencyKey, state:'in_flight'} and only a reconciler may transition it to a terminal receipt.

Cleanup interface: cleanupOwnedResources({context, adapter}) returns {cleanupReceipt, retainedDatabaseResources, retainedProviderResources, databaseBaselineRestored:false, fixtureReusable:false}; it releases lock and reservation only after a complete independent reconciliation and append-only receipt commit.

Manifest interface: canonical manifest contains exact source/run/attempt identity, immutable deployment SHA/tree, schema/migration fingerprints, contract version/digest, all 43 terminal results, and cleanup/retention receipt; a separate verifier accepts only exact 43/43 and a matching activation/run provenance.
